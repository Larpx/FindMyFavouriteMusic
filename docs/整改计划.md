# FindMyFavouriteMusic 整改计划 v1

## 一、总目标

让程序在以下方面更稳、更省、更好用：

1. **运行时切模型**：旧 ONNX Session 必析构，不驻留内存  
2. **音频硬限制**：单文件 ≤ **200MB**  
3. **设置全持久化**：可改项全部写入用户配置，重启可恢复  
4. **解析结果入库 + MD5 缓存**：未变则跳过重算  
5. **音乐库详情编辑**：选中/右键打开右侧详情，查看与编辑封面与标签字段  

---

## 二、范围边界

| 做 | 不做（本轮） |
|----|--------------|
| 上述 5 项目标 + 审计中的正确性/资源问题 | 分类模型训练（逻辑回归/LightGBM） |

## 三、阶段划分与可验证目标

### 阶段 A — 资源与安全基线（P0）

| 编号 | 事项 | 验收 |
|------|------|------|
| A1 | 模型热切换：新 session 创建成功后原子替换；**Dispose 旧 session**；提取器/工厂可释放 | 连续切换 N 次无泄漏；Host 退出释放 |
| A2 | 加载模型 ↔ 扫描/预测 **互斥**（锁或队列） | 并发操作不崩、不 `ObjectDisposedException` |
| A3 | 加载失败不破坏当前可用模型 | 坏路径加载失败后仍可推理 |
| A4 | 解码前文件大小硬限 **200MB**（扫描/预测/拖拽统一） | 超限明确失败文案 |
| A5 | 修 `PredictAsync(int)`：检查 `AcousticMeanVectorBlob` | 有画像时按 ID 预测成功 |
| A6 | 画像一致性：空喜欢清空；Like no-op；声学/深度样本数分别持久化 | 取消全部喜欢后不可用旧画像；重复 Like 不污染 |

**阶段出口：** 切模型稳、大文件被拦、ID 预测与画像行为正确。

---

### 阶段 B — 数据契约与 MD5 缓存（P1）

| 编号 | 事项 | 验收 |
|------|------|------|
| B1 | DB migration（`PRAGMA user_version`） | 旧库可升级不炸 |
| B2 | Songs 扩展字段（建议）：`FileMd5`、`FileSize`、`DurationMs`、`Format`、`AcousticDim`、`DeepModelType`、`DeepDim`、`FeatureExtractedAt`；以及元数据镜像字段（见阶段 D） | 库中可查解析结果与指纹 |
| B3 | 解析前算 **文件内容 MD5**：未变且契约匹配 → 跳过解码/提特征；可只补缺（如仅缺深度） | 二次扫描大量 skip；改音频后重算 |
| B4 | 切深度模型后：按 `DeepModelType`（+ 路径/版本若需要）判定深度向量是否过期；声学在 MD5 未变可保留 | 不会 VGGish/MERT 混维污染画像 |
| B5 | UserProfile 增加 `AcousticSampleCount` / `DeepSampleCount`（配合 A6） | 增量更新数值正确 |
| B6 | **元数据回写后的缓存策略**（与 D 联动）：标签写入会改文件 MD5，但音频流通常不变 → 元数据保存路径应 **更新 MD5，默认不清向量**；仅当音频实质变化时才重提特征 | 改封面/标题后不触发无意义重算 |

**阶段出口：** 二次扫描省算力；切模型深度重提规则清晰；标签编辑不误伤特征缓存。

---

### 阶段 C — 设置全量持久化（P1）

| 编号 | 事项 | 验收 |
|------|------|------|
| C1 | 持久化当前缺口：`AcousticOnlyWeight`、`OpenVinoCacheDir`、`MaxConcurrentProcessing`；以及设置页已有项继续保存 | 重启后全部恢复 |
| C2 | `SemaphoreSlim` 串行写 + 临时文件原子替换；配置校验（枚举/路径/权重） | 并发保存不丢、不坏 JSON |
| C3 | 配置目录迁到用户级 AppData（避免装目录写权限/symlink） | 标准用户可写、可热重载 |

**建议「所有设置」清单（须持久化）：**

- Prediction：`AcousticWeight`、`DeepWeight`、`AcousticOnlyWeight`  
- OnnxModel：`EnableDeepFeatures`、`ModelType`、`VggishModelPath`、`MertModelPath`、`ExecutionProvider`、`OpenVinoDevice`、`OpenVinoCacheDir`  
- Scan：`LastScanDirectory`、`MaxConcurrentProcessing`（`SupportedExtensions` 可先只读默认）  
- （可选本轮）FeatureExtraction 用户可改项  

**阶段出口：** 改设置 → 关开应用 → UI 与运行时一致。

### 阶段 D — 音乐库详情与元数据编辑（新功能）

#### D1. UI 交互（音乐库）

- 布局：左侧列表 / 右侧**详情面板**（未选中时显示空态提示）  
- 入口：  
  - 单击列表项 → 选中并打开详情  
  - 右键菜单：「查看详情」「编辑标签」（等价打开详情并聚焦可编辑区）  
- 详情区能力：封面展示、字段表单、保存/放弃、更换封面、清除封面  

#### D2. 字段可编辑性矩阵

**可编辑（写回标签 + 同步 DB）**

| 字段 | 说明 |
|------|------|
| 封面 (Cover) | 显示/更换图片/清除；写入 embedded picture |
| 标题 Title | |
| 艺术家 Artist | 表演者 |
| 专辑 Album | |
| 专辑艺术家 AlbumArtist | |
| 流派 Genre | |
| 年份 Year | |
| 曲目号 Track | 如 `3` 或 `3/12`（实现时定一种） |
| 碟号 Disc | 可选 |
| 注释 Comment | 可选 |
| 歌词 Lyrics | 可选（大字段，可折叠） |

**只读（展示用，不可改）**

| 字段 | 来源 |
|------|------|
| 文件路径 / 文件名 | 文件系统 |
| 格式 | 容器类型 |
| 文件大小 | FileInfo（并受 200MB 约束展示） |
| 时长 | 解码/标签侧只读信息 |
| 采样率 / 声道 / 比特率（能取到则显示） | 技术属性 |
| 文件 MD5 | 缓存指纹 |
| 特征状态 | 有无声学/深度、维度、DeepModelType |
| 喜欢状态 | 可在列表改；详情可显示，是否允许在详情切换 Like 可选 |
| 数据库 Id | 内部 |

#### D3. 技术实现要点

- 引入成熟标签库（建议 **TagLibSharp**），统一处理 MP3 / FLAC / M4A / OGG（WAV 标签能力弱：可读尽量展示，写回失败给明确提示）  
- 扫描入库时：**读取标签填充 DB**（替换当前「仅文件名当 Title、Artist=null」）  
- 保存流程：校验 → 写文件标签 → 更新 DB 镜像字段 → **更新 FileMd5，保留特征向量**（见 B6）→ 刷新列表与详情  
- 封面：内存预览；保存时嵌入；大图可限制边长/体积避免撑爆标签  
- 只读文件 / 无写权限：禁用保存并提示  
- 脏检查：有未保存修改时切换歌曲要确认  

#### D4. 数据模型扩展（与 B2 合并）

Songs 建议新增镜像列：`Album`、`AlbumArtist`、`Genre`、`Year`、`Track`、`Disc`、`Comment`、`Lyrics`（或大字段按需）；**封面不入库**。  

**已确认：方案乙** — 封面只存在音频文件内嵌 picture；详情打开时用 TagLib **实时从原文件读取**；保存时写回原文件（APIv2/FLAC picture / M4A covr 等）。列表可不显示封面或仅详情显示。

#### D5. 验收

- 选中歌曲右侧出现详情；右键可打开  
- 可编辑字段可改并写回文件；只读字段不可编辑  
- 封面可显示/更换/清除（格式支持范围内）  
- 保存后列表 Title/Artist 等立即更新；重启后 DB 与文件标签一致  
- 仅改标签不触发特征重算；改音频内容后 MD5 变且重算  

**阶段出口：** 音乐库「列表 + 右侧详情编辑」闭环可用。

## 四、推荐实施顺序（合并依赖）

```text
1. A1–A4（模型析构/互斥 + 200MB）
2. B1 + B2/B5（migration + 表结构，含元数据列占位）
3. B3–B4 + A5–A6（MD5 缓存 + 预测/画像正确性）
4. C1–C3（设置全持久化）
5. D1–D5（详情面板 + 标签读写；挂钩 B6）
6. E → F
```

每步都有上表验收；优先保证 **可验证小步合入**，避免一次大爆炸改动。

## 五、风险与设计取舍

1. **标签写回改 MD5**：必须走「元数据保存更新指纹、默认保留向量」，否则每次改封面都会重提特征。  
2. **格式能力不均**：WAV/部分 OGG 写封面或字段可能失败 → 按格式降级并提示，不假装成功。  
3. **TagLib 与 NAudio 并存**：标签走 TagLib，PCM 仍走现有解码；详情只读技术字段可部分来自 TagLib，部分来自已存 DB。  
4. **切模型与详情无强耦合**，但深度契约字段要在详情「特征状态」只读区展示，便于排障。

### 封面写入说明（技术）

可以，主流格式支持把封面嵌进音乐文件本身（不是 sidecar、也不是数据库）：

| 格式 | 常见机制 |
|------|----------|
| MP3 | ID3v2 APIC frame |
| FLAC | METADATA_BLOCK_PICTURE |
| M4A/AAC | `covr` atom |
| OGG/Vorbis | METADATA_BLOCK_PICTURE（能力因实现略有差异） |
| WAV | 标签能力弱，写封面可能失败 → 明确提示 |

实现走 **TagLibSharp** 的 `IPicture` / Pictures 集合：打开详情读、保存时替换或清空后 `Save()` 写回原路径。DB 只镜像文本标签字段（便于列表检索），封面永远以文件内嵌为准。
